Web Sound Art & RNBO

Taking Back the Web

June 16, 2026

See the interactive project here.

I. Introduction

The internet- the amorphous monolith created by all of our computers being able to almost instantly communicate with every single other computer- has laid its worth as being the centerpoint of a vast number of peoples’ lives. Is this a good thing? Not really anymore. (1). But it still is good (2). Or maybe not? (3) Well at least we know it's important (4).

In thinking about this topic from an artist’s perspective, there is an obvious benefit of the internet in its ability to disperse content (whether that be “media,” “art,” “content,” or “slop”) to an audience. It allows for small independent artists to, on a low budget, be discovered by fans hundreds of miles from their concert stages and galleries. But, the pervasiveness of content means an economy of attention (5). What can we do as artists to harness the power of the internet without squeezing dry the world of its ability to pay attention to what is being said?

There was an era of the internet where being a creator was not a losing battle. The internet that spawned the y2k aesthetic, with customized myspace pages and that lacked corporate presence. When I look at the lingering aesthetics of the internet (the one I am too young to have experienced), I see one big thing lacking today: intentionality around space. Many artists rely on platforms that are not theirs and in a way lose the ability to be intentional about the space where their art lives. In the vast digital canvas of HTML this should be the opposite. It should be physical galleries where artists must place their art in someone else’s space. The internet should be the place of infinite customizability.

Obviously that is wishful thinking to some degree, but there is still room for some intentionality. The folks at websoundart.org certainly believe so. So, as sound artists, how do we take back the internet? It requires the effort to learn how to build in digital space (*cough* coding *cough*), and the compositional mindset that comes with computer music and software programming. But it is very possible within numerous frameworks to develop the appropriate program: all we have to do is choose one and then start creating.

II. Programming Framework

The framework for embedded interactive sound I have chosen is traditional web development languages HTML, CSS, and JavaScript combined with the audio specific language RNBO. RNBO is developed by Cycling74 as a part of the MaxMSP visual DSP language. RNBO code is edited and compiled inside the MaxMSP environment and can be exported to a variety of formats: in this case WebAssembly for use with JavaScript. After the sound engine is built using RNBO, it can be controlled using JavaScript with an interface written in HTML and CSS.

RNBO’s advantages lie in its similarities to MaxMSP, a language many sound artists are already either familiar with or fluent in. Its graphical nature allows for complicated signal processing to be displayed as a network of cables (visually resembling a modular synthesizer where patch cables connect various analog signal generators). Because there are a vast number of resources for learning and debugging MaxMSP code it is easy to construct modular systems where MaxMSP components are translated into RNBO syntax with little difference in functionality.

This exploration of RNBO as a tool does not aim to compare directly the two syntaxes, but throughout the process of building this project it was a common occurrence to have two windows- one with a functioning max patch and the other with a slightly mirrored RNBO environment- open simultaneously.

A compiled RNBO patch receives data in multiple formats: “inports,” “params,” and outputs data through “outports” and signal outputs. Setting up the interface with JavaScript just requires exposing the I/O and passing data into RNBO with a script. Cycling74 provides a debug template which includes these scripts; for this project the template served as a base for the rest of the code. This made the initial setup process extremely simple.

The “game” aspect (i.e. the narrative text, user input, distance, and perlin noise field) were all constructed using java script and then the data points were passed into RNBO for the sound component. In this context, RNBO served essentially the same function as Wwise or FMOD would in the context of a game engine. The workflow is also similar: RNBO code is written and tested using the MaxMSP environment, code is compiled, and then is tested on the website. The exact same process can be seen with Unity and Wwise, for example: audio triggers and logic are set up, tested within the Wwise environment, soundbanks are generated, and then inside the Unity editor the same sound testing process occurs in the game environment.

The resulting framework is extremely flexible and lightweight. The only loading times occur upfront as the RNBO dependency is fetched, the WebAssembly is parsed, and audio files are loaded into buffers. This took around 4-5 seconds for a complex piece of code with about 85MB of audio files being served and a 612KB (.json) RNBO patch. Alongside the larger game of “TryAllYouWant,” I was able to use the exact same workflow to build a smaller, more lightweight homepage unit which still has larger audio files but is a smaller piece of WebAssembly to decode: 26MB of audio and 363KB RNBO patch. While a 4-5 second load time would be unreasonable for use cases like displaying a playlist of audio files, the upfront loading time is exchanged for a completely client side synthesis engine. This makes the more complex task of real-time synthesis and audio playback much more reasonable for an interactive experience.

III. Compositional Result(s)

“Composing” a piece of sound art in this format first and foremost requires an understanding of the possibilities with and the requirements of the underlying structure of functionality. This is true of any interactive system- whichever framework drives the interactivity also limits it. Where MaxMSP and RNBO have succeeded is by-and-large having less limitations than possibilities. This is also true of JavaScript and the various functionalities of web architecture: we (as the audio designers) can interface with the user of a site in numerous ways including the direct access of user hardware like mouse and keyboard data. MDN’s documentation for these interactive functions are extremely well written and easy to parse for artists whose focus has never been involved in software development.

Early compositional choices were to have the piece be modular and largely collage-based: where smaller sound snippets were spread out across the larger environment. In thinking of form, there was a decision made to stretch the time aspect of the piece across 50 unspecified units and to create a random field of values that could be read as the user moved across 2D space. Using a perlin noise algorithm, we can imagine this virtual landscape as being a random generation of hills and valleys where the noise values are comparable to the elevation at that point.

The user moves by providing inputs (pressing keys or moving the mouse) and slowly incrementing their position forwards in either the x or y axis (north or east). Position is displayed as a vector: distance and angle relative to the starting point of (0, 0). This creates an atmosphere of mystery where the user might not be sure what their input was directly affecting- a mood desirable for the piece’s aesthetic. This aesthetic was further implemented in deciding that the elevation value (seen across the code named “noise return”) would not be a labelled value at all.

In the sound, the various field recording and synthesis modules are modulated by the same LFOs and filter resonators, but there is also a cross modulation component that increases in intensity as the distance progresses. As the piece progresses towards the “apex” of 50, the sound becomes more affected by modulation sources. These decisions all came from a desire to balance the exploratory nature with a more linear progression of intensity. While the sound at any one given moment is random, it still follows a set progression in intensity.

The composition of this piece takes advantage of simple interface options- keyboard and mouse. Early iterations of the piece also saw interaction with gamepads (game controllers like Xbox, Playstation, etc.). The inputs control various RNBO parameters but they do not access synthesis parameters directly. Rather, the input is passed into RNBO via parameters and inports named “keyCode,” “mouse_x” etc. and the mapping to parameters is done inside the RNBO code. Intensity is progressed in the degree to which mouse and keyboard inputs affect the sound. In a way, it doesn’t just become more chaotic, it just becomes more responsive to the user’s input.

The last component, the narrative structure, was inspired by web artwork where the computer is seen as an adversary. The computer, or maybe the code itself, being a barrier fits closely with the aesthetic of fighting back against the machine to create art on the web. There is also a tactile feeling of struggle against the code, where it should be uncomfortable to have to provide so much input just to move small amounts and discover new sounds.

IV. Conclusion

The framework allowed for a vast number of compositional choices. Enough, in fact, that I think the overwhelm of possibility set in as soon as I had realized what the JS/RNBO combo would make possible. But, I think that this shaped the result immensely. It was the act of exploring possibility that allowed for different interactive elements to take shape- especially the “game” aspects that mostly live inside of the JS.

This method for web art is now, thanks to the Web Audio API and tools for compiling to WebAssembly, extremely accessible and learnable. The app that I made for my homepage is a great example of small compositional units that can be woven into the fabric of artists’ portfolios and biographies. And, it shows that we as sound artists specifically care deeply about the way our sites sound as much as we do how they look.

I want to thank the authors who have published on websoundart.org for their organization of numerous resources into a single place that is memorable and accessible. That is something that reflects what the internet can be, not what it is turning into.
